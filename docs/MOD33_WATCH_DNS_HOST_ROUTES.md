# ZDT-D 4.2.0 · mod33 — DNS для часов без перехвата обычного трафика

Продолжение mod32. Пользователь сообщил, что Galaxy Watch 7 по Bluetooth дошли до приветствия Gemini, затем сообщили об отсутствии интернета. Причина на самом устройстве пока не подтверждена.

## Найденное отличие и исправление

Предоставленный APK — `com.frostnerd.smokescreen`, версия `2.1.2-adblock`, versionCode 80. Статическая проверка APK и официальный исходный код Nebulo показали использование отдельных маршрутов к DNS-адресам, а не default route для всего трафика. Исходный код: https://github.com/Ch4t4r/Nebulo/blob/master/app/src/main/java/com/frostnerd/smokescreen/service/DnsVpnService.kt (`createBuilder`).

В mod32 Android VPN направлял весь IPv4/IPv6-трафик выбранных Samsung-приложений через HEV → loopback SOCKS DNS-профиля; sing-box затем отправлял обычные соединения напрямую. В mod33 убраны `0.0.0.0/0` и `::/0`: в TUN поступают только маршруты `/32` и `/128` к виртуальным DNS, известным публичным резолверам и DNS доступных физических сетей на момент включения. Остальные соединения выбранных приложений идут непосредственно по обычной сети телефона, обходя HEV и DNS-профиль. Обе семьи адресов разрешены; VPN следует системной сети.

Имена публичных резолверов не разрешаются через сеть: маршруты строятся только из IP-литералов. Адреса loopback, any-local, multicast и link-local не добавляются. Дополнительные адреса DNS физических сетей фиксируются при включении; после смены сети редкий жёстко заданный DNS нового оператора может потребовать выключить и включить режим. Виртуальные и известные публичные DNS-маршруты сохраняются.

Рабочий root per-app DNS, его назначения, конфиги sing-box, netd, DNS-порты и системная раздача не меняются. Существующий sing-box продолжает перехватывать UDP/TCP порт 53. Код Nebulo не переносился в проект. HEV остаётся транспортом DNS-маршрутов; mapdns/FakeIP нет. На DNS-адресах другие порты также технически попадают в TUN и идут напрямую через профиль; DoH стороннего приложения не преобразуется в DNS-профиль.

## Диагностика

На экране «DNS для часов» отображаются реальные счётчики HEV: отправленные и полученные IP-пакеты на DNS-маршрутах. Это не число DNS-вопросов и не проверка работоспособности Gemini. Счётчики обновляются раз в 5 секунд; синтетические запросы ZDT-D обходят TUN и в них не попадают. Чтение счётчиков разрешено только владельцу активного native-сеанса и не останавливает VPN при недоступности статистики.

Кнопка «Проверить DNS и скопировать отчёт» выполняет настоящие DNS-запросы через выбранный профиль: example.com по UDP и TCP, A для gemini.google.com, generativelanguage.googleapis.com и www.google.com, AAAA для gemini.google.com. Это примеры доменов, а не полный перечень служб Gemini для Wear OS. Отчёт содержит адреса ответов, DNS-коды, время, счётчики, состояние профиля и тип сети телефона. Пустой успешный AAAA-ответ нормален для DNS-профиля с IPv4-only. Проверяются ID, границы пакета и ресурсных записей.

Отчёт не включает DoH endpoint/путь/токен, ссылку подписки, API-токен, SSID или содержимое пользовательского трафика. В нём есть выбранные пакеты приложений и ответы DNS. Открой Gemini на часах, подожди 10–15 секунд и скопируй отчёт, если ошибка повторится. Нулевые счётчики означают, что захвата на этих маршрутах не зафиксировано; положительные счётчики сами по себе не доказывают запросы именно Gemini.

## Обновление и проверка

Для исправления достаточно APK mod33 поверх mod32; backend модуля mod32 совместим. ZIP mod33 можно установить для одинаковой версии APK и модуля. Перед обновлением выключи «DNS часов», после обновления включи снова; выбор профиля и Samsung-приложений сохранится.

Release CI выполняет тесты host-only маршрутов, владения HEV и доступа к статистике, реальные loopback SOCKS UDP/TCP DNS-тесты, SERVFAIL, пустой AAAA, неверный ID и повреждённый ответ, существующие сетевые проверки и сборку APK/ZIP. Приветствие на часах не является доказательством исправления; Bluetooth-транспорт Samsung и Gemini проверяются отдельно на устройстве. DNS-режим не меняет внешний IP обычных соединений, поэтому успешная работа HAPP с зарубежным сервером не доказывает достаточность DNS.
